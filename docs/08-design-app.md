# 第8章 要件・画面・API設計

コードを書く前に、**何を作るか**を決めます。
設計を端折ると、あとで「やっぱりこのカラムが要る」「画面の作り直し」が起きます。
時間をかけてやる必要はないですが、**通しで一回考えておく**ことが大切です。

設計を後回しにしてコードから書き始めると、動くには動くけど「テーブルの列が足りない」「画面をやり直す」
といった手戻りが起きやすくなります。特に DB のテーブル構造は、いったんデータが入り始めると
変更のコストが一気に上がります（カラムの型を変えるだけで既存データが壊れることもあります）。
逆にこの章でやるような紙の上の設計は、間違えてもすぐ書き直せる**失敗のコストが低い場所**なので、
ここでしっかり考えておく価値があります。

この章で決めるもの:

- 機能要件 / 非機能要件 / 「やらないこと」
- 画面のラフ
- API の表

DB 側の設計（テーブル・マイグレーション）は次章で扱います。

## 8.1 要件（最低限の仕様）

このアプリは **個人で使う ToDo リスト** とします。
複数人で共有することは考えません（ユーザー認証は範囲外）。

機能要件:

- ToDo の **追加・編集・削除・完了切替** ができる
- 一覧で「未完了」「完了」「全部」を **絞り込みできる**
- 各 ToDo は **タイトル・期限・優先度・完了フラグ** を持つ
- ToDo に **タグ** を 0 個以上付けられる（多対多）
- 一覧は **期限が近いもの・優先度が高いもの**を上に並べる
- 検索（タイトルの部分一致）ができる

機能要件が「**何ができるか**」だとすると、次の非機能要件は「**どれくらいうまく動くか**」という
品質の話です。パフォーマンスや上限件数のような数字を先に決めておくと、後で「この速度で十分なのか」
「もっと最適化すべきか」を判断する基準になります。

非機能要件（軽く）:

- 初回画面表示が 1 秒以内
- ToDo は最大 1 万件くらいまで普通に動く
- 個人 PC で動かす前提（外には公開しなくてよい）

機能の **「やらないこと」** も決めておきます。

- ユーザー登録・ログイン
- リマインダー通知
- スマホアプリ
- データのエクスポート

!!! tip "やらないことを書く"
    やる機能だけを書いていると、つい「あ、これも要るかも」が増えていきます。
    **「これはやらない」と紙に書く**だけで、ぐっと迷いが減ります。

## 8.2 ユースケース図（言葉で）

**ユースケース**とは「誰が」「何をするか」を短い動詞句で書き出したものです。
本格的な UML のユースケース図はもっと厳密な記法を使いますが、研修ではそこまでせず、
**箇条書きで十分**です。ここで先にユーザーの行動を洗い出しておくと、次の 8.3（画面）や
8.4（API）で「あれ、この操作の画面がない」「このAPIが抜けている」といった漏れに気づきやすくなります。
実際、下の一覧はほぼそのまま 8.4 の API 一覧の行に対応しています。

ユーザーは 1 人なので、シンプルに:

```text
ユーザー ──┬── ToDo を追加
          ├── ToDo の一覧を見る（絞り込み・検索付き）
          ├── ToDo を完了にする / 戻す
          ├── ToDo を編集する
          ├── ToDo を削除する
          └── タグを付ける / 外す
```

## 8.3 画面設計（軽く）

ページは **1 枚** にします。
ヘッダ・フィルタ・リスト・追加フォームの 4 ブロック。

こういう **ラフ**（wireframe）は、Figma のような専用ツールを使わなくても、テキストの箱で十分です。
目的は見た目を作り込むことではなく、**画面にどんな情報とボタンが並ぶかを先に合意しておく**ことです。

```text
┌──────────────────────────────────────────┐
│  ToDo                            [追加]   │  ← ヘッダ
├──────────────────────────────────────────┤
│  [全て] [未完了] [完了]   [ 検索…       ] │  ← フィルタ
├──────────────────────────────────────────┤
│  ☐ 牛乳を買う      5/8 高 [家事]         │
│  ☐ 健康診断の予約  5/9 高 [健康]         │
│  ☑ 領収書の整理    --  中  [仕事]         │  ← リスト
│  ☐ 車検の見積もり  6/1 中                │
├──────────────────────────────────────────┤
│  [ タイトルを入力…   期限   優先  追加 ]  │  ← フォーム
└──────────────────────────────────────────┘
```

UI は [htmx](https://htmx.org/docs/) でゆるく動かすので、**ボタンを押したら部分的に書き換える**動きにします。
htmx は、JavaScript をほとんど書かずに「サーバーが返した HTML の断片で、ページの一部だけを
差し替える」ことができるライブラリです。ボタンを押すたびにページ全体を再読み込みしなくて済むので、
体感の速さが上がります。（具体的な実装は第15・16章）

## 8.4 API 設計

「画面 → サーバー」のやりとりを **小さな表** にしておきます。
URL の付け方は「**リソース指向**」を意識します（複数形 + 動詞は HTTP メソッド）。

これは **REST** と呼ばれる考え方の中心的なアイデアです。`/getTodos` や `/deleteTodo?id=1` のように
URL に動作（動詞）を埋め込む代わりに、URL は「ToDo という**リソースの集まり**」を指す名詞
（`/api/todos`）だけにして、「何をするか」は
[HTTP メソッド](https://developer.mozilla.org/ja/docs/Web/HTTP/Methods)
（`GET` / `POST` / `PATCH` / `DELETE` など）で表現します。こうしておくと URL の一覧を見ただけで
「このアプリにはどんな種類のデータがあるか」が分かりやすくなり、同じ `/api/todos` という URL を
メソッド違いで使い回せるので表もすっきりします。

| メソッド | パス | 役割 | リクエスト | レスポンス |
|---|---|---|---|---|
| `GET`    | `/`                   | 画面表示（HTML）          | クエリ: `filter`, `q`              | HTML                 |
| `GET`    | `/api/todos`          | ToDo 一覧（JSON）         | クエリ: `filter`, `q`              | `Todo[]`             |
| `POST`   | `/api/todos`          | ToDo 作成                 | JSON: `{title, due_on?, priority?, tags?}` | `Todo`        |
| `PATCH`  | `/api/todos/{id}`     | ToDo 部分更新             | JSON: 任意フィールド               | `Todo`               |
| `POST`   | `/api/todos/{id}/toggle` | 完了/未完了の切替      | （なし）                           | `Todo`               |
| `DELETE` | `/api/todos/{id}`     | ToDo 削除                 | （なし）                           | `204 No Content`     |
| `GET`    | `/api/tags`           | タグ一覧                  | （なし）                           | `Tag[]`              |

!!! note "ステータスコードも設計のうち"
    表の「レスポンス」には返す値の中身しか書いていませんが、実際には
    [HTTP ステータスコード](https://developer.mozilla.org/ja/docs/Web/HTTP/Status) もレスポンスの
    一部です。この研修で使うのは主に次の使い分けです。

    - `200 OK`: 取得・更新が成功した（レスポンスボディあり）
    - `201 Created`: 新しく作成できた（`POST /api/todos` の成功時）
    - `204 No Content`: 成功したが返す本文がない（削除の成功時など）
    - `404 Not Found`: 指定した `id` の ToDo が存在しない
    - `422 Unprocessable Entity`: 送られてきた JSON の形は正しいが値がおかしい（FastAPI が自動で返す）

    ステータスコードを使い分けておくと、クライアント側（htmx やテストコード）はレスポンスの
    中身を見なくても「成功したか失敗したか」を判定できます。実装は第14章で扱います。

!!! note "冪等性（べきとうせい）を意識する"
    [冪等性](https://developer.mozilla.org/ja/docs/Glossary/Idempotent) とは、
    「同じリクエストを1回投げても2回投げても、サーバー側の結果が同じになる」性質のことです。
    `GET` / `PUT` / `DELETE` は基本的に冪等です（同じ ToDo を2回消しても、1回目で消えていれば
    2回目は `404` になるだけで、状態としては「存在しない」のまま変わりません）。一方
    `POST /api/todos` は呼ぶたびに新しい ToDo が1件増えるので冪等ではありません。

    表の `POST /api/todos/{id}/toggle` は少し注意が必要な例です。「今の状態を反転する」という
    操作なので、**2回叩くと元に戻ってしまいます**。1回のリクエストと2回のリクエストで最終的な
    状態が変わってしまうため、厳密には冪等ではありません。もし冪等にしたいなら、
    `PATCH /api/todos/{id}` に `{"done": true}` を送るような「状態そのものを指定する」設計にする
    という手もあります。今回は UI 側の使いやすさを優先して `toggle` を採用していますが、
    こういうトレードオフがあることは覚えておいてください。

レスポンスの「形」も先に決めておきます。実装では
[Pydantic](https://docs.pydantic.dev/latest/) というライブラリでこの形をクラスとして定義し、
FastAPI がリクエスト/レスポンスの値がこの形に沿っているかを自動でチェックしてくれます
（詳しくは第13章）。ここではコードを書く前に、まず日本語混じりの疑似コードで形を決めておきます。

Todo / Tag のスキーマ（Pydantic で表現する想定）:

```text
Todo {
  id: int
  title: string
  done: bool
  due_on: date | null
  priority: 1 | 2 | 3
  tags: string[]
  created_at: datetime
  updated_at: datetime
}

Tag {
  id: int
  name: string
}
```

!!! tip "PATCH と PUT の使い分け"
    - **`PUT`** はリソースを「丸ごと差し替える」
    - **`PATCH`** はリソースを「部分的に書き換える」

    今回は「タイトルだけ変えたい」「優先度だけ変えたい」が普通なので `PATCH` を採用します。

## 8.5 ディレクトリ構成

コードを書き始める前に **ディレクトリ構成を決めておく**のにも理由があります。
あとから「この処理はどこに置くべきか」を都度悩んでいると、似たような処理があちこちに散らばってしまい、
変更やテストのときにどこを触ればいいか分かりにくくなります。先に器（フォルダとファイルの役割）を
決めておけば、新しい機能を追加するときも「ここに置けばいい」と迷わずに済みます。

研修で実際に使う構成です。

```text
sample/todo-app/
├── app/
│   ├── __init__.py
│   ├── main.py              # FastAPI アプリ起動点
│   ├── config.py            # 設定（環境変数）
│   ├── db.py                # 接続管理（プール）
│   ├── models.py            # ドメインモデル（dataclass）
│   ├── schemas.py           # Pydantic スキーマ（API用）
│   ├── repositories.py      # SQL を投げる層
│   ├── services.py          # 業務ロジック層（軽く）
│   ├── routers/
│   │   ├── __init__.py
│   │   ├── pages.py         # GET / の HTML 返却
│   │   └── todos.py         # /api/todos の CRUD
│   ├── templates/           # Jinja2
│   └── static/              # CSS
├── migrations/
│   ├── 001_init.sql
│   └── 002_seed.sql
├── tests/
└── pyproject.toml
```

レイヤーの考え方:

```text
HTTP（FastAPI ルーター）
   ↓ Pydantic で入力チェック
Service（業務ロジック）
   ↓ ドメインモデル（dataclass）
Repository（SQL 発行）
   ↓
PostgreSQL
```

各層の責務:

- **routers**: HTTP の世界（リクエスト/レスポンス、ステータスコード）
- **schemas**: 入力と出力の型を定義（Pydantic）
- **services**: ビジネスルール（「未完了が 100 件超えたら警告」のような）
- **repositories**: SQL を書く場所
- **models**: アプリ全体で使うドメイン型（dataclass）

この図の矢印は**依存の向き**でもあります。上の層（routers）は下の層（repositories）の存在を
知っていますが、逆に repositories が routers を知ることはありません。こう一方向にそろえておくと、
「repositories だけを HTTP を経由せずにテストする」（第12章）といったことがやりやすくなります。
層を分けずに1つの関数に全部書いてしまうと、こうした部分的なテストがしづらくなり、
何かを確認するたびに毎回サーバーを起動して DB までつなぐ必要が出てきます。

研修では **services は薄く** して、ほぼ routers ↔ repositories で完結します。

## やってみよう

1. 自分なら ToDo に **どんなカラムを追加したいか** 3 つ挙げる
   （例: 説明文、繰り返し設定、リマインド時刻）。
2. その追加カラムに対して、**API としてどうリクエストを受け取るか**を、
   この章の表に行を 1 つ足す形で書いてみる。
3. 「やらないこと」のリストに、自分なら何を追加するか考えてみる。

次は [第 9 章 テーブル設計とマイグレーション](09-design-db.md) で、
**DB 側の設計**をして、それをコードで管理する方法を作ります。
