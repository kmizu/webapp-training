# 第8章 要件・画面・API設計

ここからは、いよいよ ToDo アプリ本体に入ります。
ただし、いきなりコードは書きません。この章では **何を作るかを紙の上で決める**
作業（設計）を行い、第10章以降の写経の準備を整えます。

## 8.1 この章でやること

この章が終わったときに、次のことができる状態を目指します。

- 「なぜコードより先に設計するのか」を説明できる
- HTTP リクエスト／レスポンスの構成要素（メソッド、URL、ボディ、ステータスコード）を
  挙げられる
- REST API の「URL は名詞、操作は HTTP メソッド」という考え方を説明できる
- 作るアプリの要件・画面・API を、自分の言葉で説明できる
- 第10章以降の写経で使う `mytodo/` ディレクトリを作成済みにする

**所要時間の目安: 60 分**

この章で書くのは文章と図だけで、動かすコードはありません。
最後に `mytodo/` ディレクトリを 1 つ作るだけです。

## 8.2 前提知識

Web アプリの設計に入る前に、3 つの概念を押さえておきます。

!!! note "なぜ設計してから書くのか"
    コードから書き始めても、動くものはできます。ただ、途中で
    「やっぱりこのカラムが要る」「画面をやり直したい」となったとき、
    **すでに書いたコードと、すでに入ったデータ**が重りになって、修正のコストが
    一気に跳ね上がります。特に DB のテーブル構造は、データが入り始めると
    型を 1 つ変えるだけでも既存データの移行が必要になります。

    逆に、紙の上の設計は間違えても消して書き直すだけです。
    **失敗のコストが一番低い場所で、一番多く間違えておく**のが設計の役割です。
    完璧を目指す必要はありません。「通しで一回考えた」という事実があるだけで、
    手戻りは激減します。

!!! note "HTTP リクエスト／レスポンスの基礎"
    Web アプリでは、ブラウザ（クライアント）とサーバーの間で
    **HTTP** という約束事に沿ったメッセージの往復が行われます。

    クライアントが送る**リクエスト**の主な構成要素:

    - **メソッド**: 何をしたいか。`GET`（取得）、`POST`（作成）、
      `PATCH`（部分更新）、`DELETE`（削除）など
    - **URL（パス）**: どのデータに対してか。例: `/api/todos/3`
    - **クエリパラメータ**: URL の `?` 以降に付ける補足条件。
      例: `/api/todos?filter=open&q=牛乳`
    - **ボディ**: 作成・更新の中身。JSON で送ることが多い。
      例: `{"title": "牛乳を買う", "priority": 1}`

    サーバーが返す**レスポンス**の主な構成要素:

    - **ステータスコード**: 結果の種別を表す 3 桁の数字。
      `200 OK`、`201 Created`、`404 Not Found` など
    - **ボディ**: 返すデータの中身。HTML や JSON

    第14章では `curl` でこの往復を実際に観察します。
    今は「リクエストには『何を・どこに』が載り、レスポンスには
    『うまくいったか』の数字と中身が載る」ことだけ押さえておけば十分です。

!!! note "REST API とは"
    **REST** は、Web の API を設計するときの代表的な考え方です。
    中心となるルールはシンプルで、

    - **URL は「何のデータか」を指す名詞にする**（例: `/api/todos`）
    - **「何をするか」は HTTP メソッドで表す**（`GET` なら取得、`DELETE` なら削除）

    という 2 点です。`/getTodos` や `/deleteTodo?id=1` のように URL に動詞を
    埋め込む設計も可能ですが、REST では URL を「ToDo という**リソース**の
    住所」に徹します。こうしておくと、URL 一覧を見ただけでアプリにどんな
    データがあるかがわかり、同じ URL をメソッド違いで使い回せます。

## 8.3 要件（最低限の仕様）

まず「何を作るか」を文章で決めます。
このアプリは **個人で使う ToDo リスト** とします。
複数人で共有することは考えません（ユーザー認証は範囲外です）。

**機能要件**（何ができるか）:

- ToDo の **追加・編集・削除・完了切替** ができる
- 一覧で「未完了」「完了」「全部」を **絞り込みできる**
- 各 ToDo は **タイトル・期限・優先度・完了フラグ** を持つ
- ToDo に **タグ** を 0 個以上付けられる（多対多。第9章でテーブルに落とします）
- タイトルの **部分一致で検索** できる

**非機能要件**（どれくらいうまく動くか。数字は判断基準のためのもので、厳密に測りません）:

- 初回画面表示が 1 秒以内
- ToDo は最大 1 万件くらいまで普通に動く
- 個人 PC で動かす前提（外部には公開しない）

**やらないこと**:

- ユーザー登録・ログイン
- リマインダー通知
- スマホアプリ
- データのエクスポート

!!! tip "「やらないこと」を書く"
    やる機能だけを書いていると、つい「あ、これも要るかも」が増えていきます。
    **「これはやらない」と紙に書く**だけで、ぐっと迷いが減ります。

## 8.4 ユースケース（誰が何をするか）

要件を、ユーザーの行動として書き出します。
本格的なユースケース図には UML の記法がありますが、研修では箇条書きで十分です。
ユーザーの行動を先に洗い出しておくと、後で「この操作の画面がない」
「この API が抜けている」という漏れに気づきやすくなります。
実際、下の一覧はほぼそのまま 8.6 の API 一覧の行に対応します。

ユーザーは 1 人なので、シンプルに:

```text
ユーザー ──┬── ToDo を追加
          ├── ToDo の一覧を見る（絞り込み・検索付き）
          ├── ToDo を完了にする / 戻す
          ├── ToDo を編集する
          ├── ToDo を削除する
          └── タグを付ける / 外す
```

## 8.5 画面設計

ページは **1 枚** にします。
ヘッダ・フィルタ・リスト・追加フォームの 4 ブロックです。

こういう **ラフ（ワイヤーフレーム）** は、Figma のような専用ツールを使わなくても、
テキストの箱で十分です。目的は見た目を作り込むことではなく、
**画面にどんな情報とボタンが並ぶかを先に合意しておく**ことです。

```text
┌──────────────────────────────────────────┐
│  ToDo                                     │  ← ヘッダ
├──────────────────────────────────────────┤
│  [全て] [未完了] [完了]   [ 検索…       ] │  ← フィルタ
├──────────────────────────────────────────┤
│  ☐ 牛乳を買う      5/8 高 [家事]      [×] │
│  ☐ 健康診断の予約  5/9 高 [健康]      [×] │  ← リスト
│  ☑ 領収書の整理    —   中 [仕事]      [×] │
├──────────────────────────────────────────┤
│  [ やること…    期限   優先度   追加 ]    │  ← 追加フォーム
└──────────────────────────────────────────┘
```

各行の左端の `☐` を押すと完了／未完了が切り替わり、右端の `×` で削除します。
この動きには [htmx](https://htmx.org/) を使います。
htmx は、JavaScript をほとんど書かずに「サーバーが返した HTML の断片で、
ページの一部だけを差し替える」ことができるライブラリです。
ボタンを押すたびにページ全体を再読み込みしなくて済むので、体感の速さが上がります
（実装は第15・16章で扱います）。

## 8.6 API 設計

画面の操作とサーバーの処理を結びつけるのが API です。
8.2 の REST の考え方に沿って、**URL は名詞、操作は HTTP メソッド**で表を作ります。

| メソッド | パス | 役割 | リクエスト | レスポンス |
|---|---|---|---|---|
| `GET`    | `/`                      | 画面表示（HTML）      | クエリ: `filter`, `q`                    | HTML             |
| `GET`    | `/api/todos`             | ToDo 一覧（JSON）     | クエリ: `filter`, `q`                    | `Todo[]`         |
| `POST`   | `/api/todos`             | ToDo 作成             | JSON: `{title, due_on?, priority?, tags?}` | `Todo`（`201`） |
| `GET`    | `/api/todos/{id}`        | ToDo 1 件取得         | （なし）                                 | `Todo`           |
| `PATCH`  | `/api/todos/{id}`        | ToDo 部分更新         | JSON: 任意フィールド                     | `Todo`           |
| `POST`   | `/api/todos/{id}/toggle` | 完了／未完了の切替    | （なし）                                 | `Todo`           |
| `DELETE` | `/api/todos/{id}`        | ToDo 削除             | （なし）                                 | `204 No Content` |
| `GET`    | `/api/tags`              | タグ一覧              | （なし）                                 | `Tag[]`          |

`/api/todos` のように `{id}` を含まない URL は「コレクション全体」、
`/api/todos/3` のように `{id}` を含む URL は「その中の 1 件」を指します。
`/api/...` の URL が返すのは **JSON**（プログラム向けのデータ）で、
`/` が返すのは **HTML**（人が見る画面）です。

!!! note "画面の動き用の URL もある"
    実際の完成版には、この表のほかに htmx 用の URL があります
    （`GET /partials/list`、`POST /htmx/todos`、`POST /htmx/todos/{id}/toggle`、
    `DELETE /htmx/todos/{id}`）。これらは JSON ではなく **HTML の断片**
    （リスト部分だけ、行 1 つ分だけ）を返し、htmx がページの該当箇所と
    差し替えるためのものです。設計の骨格は上の表で十分なので、
    詳しくは第16章で扱います。

!!! note "ステータスコードも設計のうち"
    レスポンスにはボディだけでなくステータスコードも含まれます。
    この研修で使うのは主に次の使い分けです。

    - `200 OK`: 取得・更新が成功した（ボディあり）
    - `201 Created`: 新しく作成できた（`POST /api/todos` の成功時）
    - `204 No Content`: 成功したが返す本文がない（削除の成功時）
    - `404 Not Found`: 指定した `id` の ToDo が存在しない
    - `422 Unprocessable Content`: JSON の形は正しいが値がおかしい
      （FastAPI が自動で返します）

    ステータスコードを使い分けておくと、クライアント側はボディを見なくても
    「成功したか失敗したか」を判定できます。実装は第14章で扱います。

!!! note "冪等性（べきとうせい）を意識する"
    **冪等性**とは、「同じリクエストを 1 回投げても 2 回投げても、
    サーバー側の結果が同じになる」性質のことです。
    `GET` / `PATCH` / `DELETE` は基本的に冪等です（同じ ToDo を 2 回消しても、
    2 回目は `404` になるだけで、状態は「存在しない」のままです）。
    一方 `POST /api/todos` は呼ぶたびに ToDo が 1 件増えるので冪等ではありません。

    表の `POST /api/todos/{id}/toggle` は少し注意が必要な例です。
    「今の状態を反転する」操作なので、**2 回叩くと元に戻ってしまいます**。
    冪等にしたければ、`PATCH /api/todos/{id}` に `{"done": true}` を送るような
    「状態そのものを指定する」設計にする手もあります。
    今回は UI の使いやすさを優先して `toggle` を採用していますが、
    こういうトレードオフがあることは覚えておいてください。

!!! tip "PATCH と PUT の使い分け"
    - **`PUT`** はリソースを「丸ごと差し替える」
    - **`PATCH`** はリソースを「部分的に書き換える」

    今回は「タイトルだけ変えたい」「優先度だけ変えたい」が普通なので
    `PATCH` を採用します。

レスポンスの「形」も先に決めておきます。
実装では [Pydantic](https://docs.pydantic.dev/latest/) というライブラリで
この形をクラスとして定義し、FastAPI がリクエスト／レスポンスの値が
この形に沿っているかを自動でチェックしてくれます（詳しくは第13章）。
ここではコードを書く前に、疑似コードで形だけ決めます。

```text
Todo {
  id: int
  title: string
  done: bool
  due_on: date | null        # 期限は未設定でもよい
  priority: 1 | 2 | 3        # 1=高, 2=中, 3=低
  tags: Tag[]                # 0 個以上
  created_at: datetime
  updated_at: datetime
}

Tag {
  id: int
  name: string
}
```

API に送るとき（`POST` / `PATCH` のボディ）の形も決めておきます。
タグは **名前の配列** で受け取ることにします
（`{"title": "牛乳を買う", "tags": ["家事", "買い物"]}` のように送ると、
存在しないタグ名はサーバー側で新しく作られます）。

```text
TodoCreate（新規作成の入力）{
  title: string              # 必須、1〜200 文字
  due_on: date | null
  priority: 1 | 2 | 3        # 省略時は 2（中）
  tags: string[]             # タグ名の配列
}

TodoPatch（部分更新の入力）{
  # 全部省略可能。送られたフィールドだけ更新する
  title: string | null
  due_on: date | null
  priority: 1 | 2 | 3 | null
  done: bool | null
  tags: string[] | null
}
```

## 8.8 ディレクトリ構成

最後に、これから作るアプリのディレクトリ構成を見ておきます。
先に「どのファイルがどの役割か」を決めておくと、写経中に
「このコードはどこに置くんだっけ」と迷わずに済みます。

```text
mytodo/                        # 第10章以降、ここに写していく
├── app/
│   ├── __init__.py
│   ├── main.py                # FastAPI アプリの起動点
│   ├── config.py              # 設定（環境変数の読み込み）
│   ├── db.py                  # DB 接続管理（第7章のプールがここに入る）
│   ├── models.py              # ドメインモデル（dataclass）
│   ├── schemas.py             # Pydantic スキーマ（API の入出力の形）
│   ├── repositories.py        # SQL を投げる層
│   ├── services.py            # 業務ルール（薄く）
│   ├── cli.py                 # マイグレーション実行などのコマンド
│   ├── routers/
│   │   ├── __init__.py
│   │   ├── pages.py           # GET / など HTML を返すルート
│   │   └── todos.py           # /api/todos の CRUD
│   ├── templates/             # Jinja2 テンプレート
│   └── static/                # CSS
├── migrations/
│   ├── 001_init.sql           # テーブル定義
│   └── 002_seed.sql           # 初期データ
├── tests/                     # pytest のテスト
└── pyproject.toml
```

ファイルが多く見えますが、役割ごとに **層** に分かれているだけです。

```text
HTTP（routers: FastAPI のルーター）
   ↓ Pydantic で入力チェック（schemas）
Service（services: 業務ルール）
   ↓ ドメインモデル（models: dataclass）
Repository（repositories: SQL 発行）
   ↓ psycopg（第5〜7章で学んだ仕組み）
PostgreSQL
```

各層の責務:

- **routers**: HTTP の世界（リクエストの受け取り、ステータスコード）
- **schemas**: API の入力と出力の型の定義（Pydantic）
- **services**: 業務ルール（この研修では薄く、ほぼ routers ↔ repositories で完結）
- **repositories**: SQL を書く場所（第10・11章の主役）
- **models**: アプリ全体で使うドメイン型（dataclass）

この図の矢印は**依存の向き**でもあります。上の層は下の層を知っていますが、
逆はありません（repositories は routers の存在を知りません）。
一方向にそろえておくと、「repositories だけをサーバーなしでテストする」
（第12章）といったことがやりやすくなります。

## 8.10 つまずきポイント

この章はコードを書かないので、つまずきは「実行エラー」ではなく
**概念の誤解**として現れます。

### 「設計を完璧に仕上げるまで先に進めない」

設計は当たりを付ける作業であって、正解を確定させる作業ではありません。
この章の表や図は、実装中に変わってかまいません（実際、写経しながら
気づくことがたくさんあります）。**書き直せるからこそ設計なので、
60 分考えたらとりあえず先に進む**のが正しい使い方です。

### URL に動詞を入れてしまう

`/getTodos` や `/api/todos/delete?id=3` のような設計です。
REST では URL はリソースの住所（名詞）に徹し、操作は HTTP メソッドに
任せます。`/api/todos/3` に `DELETE` を送れば削除、`PATCH` を送れば更新です。
「URL だけ見ても何をする URL かわからない」状態こそが REST の狙いで、
メソッドとセットで初めて意味が決まります。

なお `POST /api/todos/{id}/toggle` は例外に見えますが、
これは「状態を反転する」という操作自体をリソースのサブ操作として
表現したものです。8.6 の冪等性の話と合わせて、
「厳密さと使いやすさのトレードオフ」の例として捉えてください。

### 「画面が 1 枚だから API も 1 本でいい」

画面が 1 枚でも、裏側の操作は「追加」「削除」「切替」「絞り込み」など
複数あります。API は画面の枚数ではなく、**データに対する操作の種類**で
決まります。8.4 のユースケース一覧と 8.6 の API 表がほぼ 1 対 1 に
対応していることを確認してみてください。

### `404` と `422` の区別が付かない

- **`404`**: URL が指す ToDo そのものが存在しない（「そこにデータがない」）
- **`422`**: データは届いたが、中身がルール違反
  （タイトルが空文字、優先度が `9` など。「形は合っているが値がおかしい」）

どちらも失敗ですが、原因の場所が違います。
`404` は URL 側、`422` はボディ側の問題です。

## 8.11 やってみよう

この章の練習問題は「書いて考える」タイプです。紙でもメモ帳でも構いません。
解答例は折りたたんであるので、まず自分で考えてから見比べてください。

### 問1 新しいフィールドを設計に追加する

あなたは ToDo に「**メモ**」（任意の補足説明。長文も可）を持たせたくなりました。
次の 3 つを書き出してください。

1. 8.6 の `Todo` スキーマに追加する行
2. `TodoCreate` / `TodoPatch` に追加する行
3. 8.6 の API 表は変更要るかどうか（要るならどの行がどう変わるか）

??? example "解答例"

    1. `Todo` スキーマに `memo: string | null` を追加する
    2. `TodoCreate` と `TodoPatch` の両方に `memo: string | null` を追加する
       （`TodoPatch` では省略可能なので「送られたときだけ更新」される）
    3. API 表に **新しい行は要らない**。`POST /api/todos` と
       `PATCH /api/todos/{id}` のリクエスト欄に `memo?` が増えるだけで、
       URL とメソッドの組み合わせは変わらない。
       REST では「データの項目が増える」ことと「API の入口が増える」ことは
       別の話です。項目の追加は既存の作成・更新 API がそのまま受け入れます。

### 問2 「タグで絞り込み」機能の API を考える

現状の `GET /api/todos` は `filter`（完了状態）と `q`（タイトル検索）で
絞り込めます。ここに「**タグ名で絞り込む**」機能を追加したい場合、
リクエストはどうあるべきか、URL の形（クエリパラメータ含む）で書いてください。
新しい URL を増やす案と、既存 URL に条件を足す案の両方を考え、
どちらがよいか理由も書いてみてください。

??? example "解答例"

    既存の `GET /api/todos` にクエリパラメータを足すのが自然です。

    ```text
    GET /api/todos?filter=open&tag=家事
    ```

    新しい URL（例: `GET /api/todos/by-tag/家事`）を増やす案もありえますが、
    「絞り込み条件の追加」はリソースの種類が増えるわけではないので、
    クエリパラメータで表現するのが REST らしい設計です。
    条件が増えたとき（タグ + 期限の範囲、など）も `?tag=家事&due_before=2026-09-01`
    のように足していける拡張性もあります。

    なお、実際の完成版ではこの機能は実装していません
    （`filter` と `q` のみ）。「設計で考えたことを全部実装する必要はない」
    というのも、設計の大事な使い方です。

### 問3 冪等な「完了」操作を設計する

8.6 で触れたとおり、`POST /api/todos/{id}/toggle` は冪等ではありません
（2 回叩くと元に戻る）。「通信が不安定で同じリクエストが 2 回届くかもしれない」
環境でも安全なように、**冪等な完了操作**を 8.6 の表の形式
（メソッド・パス・リクエスト・レスポンス）で 1 行設計してください。

??? example "解答例"

    | メソッド | パス | 役割 | リクエスト | レスポンス |
    |---|---|---|---|---|
    | `PATCH` | `/api/todos/{id}` | ToDo を完了状態にする | JSON: `{"done": true}` | `Todo` |

    既存の `PATCH /api/todos/{id}` に「状態そのもの」を指定して送る形です。
    `{"done": true}` は何回送っても最終状態は「完了」の 1 つなので冪等です。
    「未完了に戻す」場合は `{"done": false}` を送ります。

    実際の完成版では UI の押しやすさを優先して `toggle` を採用していますが、
    外部からプログラムで呼ばれる API ならこちらの設計のほうが安全です。

## まとめ

- 設計は**失敗のコストが一番低い場所**で間違えるための作業。
  完璧さより「通しで一回考える」ことが大事
- HTTP のリクエストは「メソッド（何を）+ URL（どこに）」、
  レスポンスは「ステータスコード + ボディ」
- REST では **URL は名詞、操作は HTTP メソッド**。
  `/api/todos` と `GET`/`POST`/`PATCH`/`DELETE` の組み合わせで表現する
- 要件 → ユースケース → 画面 → API の順に考えると、漏れに気づきやすい
- 第10章以降は **写経式**。`mytodo/` に自分で打って写し、
  `diff -u mytodo/<パス> sample/todo-app/<パス>` で答え合わせする

次は [第9章 テーブル設計とマイグレーション](09-design-db.md) で、
この章で決めた要件を **DB のテーブル構造**に落とし込み、
それを SQL ファイルで管理する方法を作ります。
