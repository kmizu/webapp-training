## 開発環境とツール

**uv / pip**
: Python のパッケージインストーラ。pip は Python 標準、uv はその高速な代替ツールです。
  uv は仮想環境の作成や Python 本体のバージョン管理も 1 つのツールでまかなえます。
  本研修では手順を統一するため uv を使います。（→ 第0章）

**仮想環境**
: プロジェクトごとに独立した Python の実行環境（専用の Python とライブラリ置き場）を作る仕組みです。
  プロジェクトごとに部屋を分けることで、ライブラリのバージョンがぶつかって壊れるのを防ぎます。
  このリポジトリでは `.venv/` ディレクトリがその部屋です。（→ 第0章）

**コンテナ / Docker**
: コンテナは「アプリが動くのに必要なもの（プログラム本体・ライブラリ・設定）をひとまとめにした箱」で、
  Docker はその箱を作ったり動かしたりするためのツールです。
  全員がまったく同じ PostgreSQL 16 をホスト環境を汚さずに動かせるのが利点です。（→ 第0章、第18章）

**ポート**
: 1 台のマシンの中で動いている複数のサービスを番号で区別する仕組みです。
  「`localhost` の 5432 番に接続する」は PostgreSQL への接続を意味します。
  すでに使われている番号を取り合うとポート競合のエラーになります。（→ 第0章）

**プロセス**
: OS の上で実行中のプログラム 1 つぶんの単位です。
  Web サーバーは起動しっぱなしのプロセスで、止めるときは `Ctrl+C` を押します。
  PostgreSQL も接続ごとに専用のバックエンドプロセスを起動します。（→ 第7章、第13章）

**ホットリロード**
: コードを変更したら自動でサーバーが再起動する仕組みです。`uvicorn --reload` で有効になります。
  開発のリズムを崩さないための開発専用の機能で、本番では外します。（→ 第13章、第18章）

## Python の言語の仕組み

**動的型付け**
: 変数の型が実行してみるまで確定しない言語仕様のことです。Python がこれにあたります。
  柔軟な反面、「この関数の引数には何を渡せばいいのか」がコードを読むだけではわからない弱点があります。（→ 第1章）

**型ヒント**
: 「この引数は `int`」「この戻り値は `str`」という注釈をコードに書き添える仕組みです。
  Python 本体は実行時にチェックしませんが、エディタや静的解析ツール、FastAPI がこの情報を活用します。（→ 第1章、第13章）

**静的解析（静的チェック）**
: プログラムを実行せずにコードを解析して問題を見つけることです。
  Pylance や mypy、pyright が代表格で、型の食い違いを書いている最中に教えてくれます。（→ 第1章）

**dataclass**
: Python 標準の「データを持つだけのクラス」を簡潔に書く仕組みです。`@dataclass` を付けて使います。
  `__init__` や `__repr__` を手で書く手間を省けます。本研修ではドメインモデルの表現に使います。
  詳しくは[公式ドキュメント](https://docs.python.org/3/library/dataclasses.html)を参照してください。（→ 第1章、第10章）

**リソースと後始末**
: ファイルや DB 接続は OS や DB サーバーから借りる有限の資源（リソース）で、使い終わったら必ず返す必要があります。
  この「返す」処理が後始末で、with 文はエラー時も含めた後始末の書き忘れを仕組みで防ぎます。
  第7章では `contextlib` の `@contextmanager` を使って、自分で with 文に対応した「プールから接続を借りて返す」仕組みを作ります。（→ 第2章、第7章）

**スタックトレース**
: 例外が発生したときに出る、関数呼び出しの履歴です。バグ調査の最初の手がかりになります。（→ 第17章）

**GIL**
: Global Interpreter Lock。Python は基本 1 プロセスで CPU を 1 スレッドぶんしか使わない仕組みです。
  本研修では深追いしません。

## テスト

**テストの自動化**
: 「こう入力したらこう返るはず」という期待をコードとして書き残し、コマンドひとつで何度でも再実行できるようにすることです。
  変更のたびに「前まで動いていたものが壊れていないか」を機械に確認させられます。（→ 第2章）

**フィクスチャ（fixture）**
: テスト関数に渡す「お膳立て」を pytest に任せる仕組みです。
  テスト関数の引数に名前を書くだけで、pytest が準備（セットアップ）と後片付け（ティアダウン）を自動で行います。
  第12章では DB 接続を渡す `conn` フィクスチャを作ります。（→ 第2章、第12章）

**テストの独立性**
: テストが書いた順番や実行した順番に関係なく、いつ・何度実行しても同じ結果になるべき、という性質です。
  DB を使うテストでは、各テストが使った変更をロールバックで巻き戻すことで確保します。（→ 第12章）

## データベースの基礎

**リレーショナルデータベース（RDB）**
: データを表（テーブル）の形で管理するデータベースです。PostgreSQL はその代表的な製品です。
  テーブル（表そのもの）、行（データ 1 件分）、列（型の決まった項目）からなる「厳格なスプレッドシート」と考えるとイメージしやすいです。（→ 第3章）

**SQL / psql**
: SQL はリレーショナルデータベースへの指示を書くための言語、psql はその SQL を PostgreSQL に送るためのコマンドラインツールです。
  `\dt` などの `\` から始まるものは SQL ではなく psql 独自のメタコマンドで、Python コードからは使えません。（→ 第3章）

**DDL / DML**
: Data Definition Language（`CREATE TABLE` などスキーマ操作）と Data Manipulation Language（`SELECT` / `INSERT` / `UPDATE` / `DELETE` などデータ操作）です。
  `SELECT` を DQL として切り離す流儀もあります。アプリのコードで書くのはほぼ DML で、DDL はマイグレーションの場面で使います。（→ 第3章）

**主キー / 外部キー**
: 主キー（`PRIMARY KEY`）は行を一意に特定するための列です。
  外部キー（`FOREIGN KEY`）は「この列の値は別テーブルの主キーとして実在していなければならない」という制約で、
  テーブル同士の参照の辻褄が合っていることを DB に保証させます。（→ 第4章）

**NULL**
: 「値がないこと」を表す特殊な値です。`0` や空文字列とは別物で、比較しても等しいとは判定されません。
  `= NULL` は真偽のどちらでもなく UNKNOWN になるため、NULL かどうかの判定には `IS NULL` / `IS NOT NULL` を使います。（→ 第3章）

**CHECK 制約**
: テーブルのカラムが守るべき条件です。`CHECK (priority BETWEEN 1 AND 3)` で「1〜3 以外は入れさせない」とできます。
  アプリ側のバリデーションの抜け漏れに備える、DB 側の最後の砦です。
  詳しくは[公式ドキュメント](https://www.postgresql.org/docs/current/ddl-constraints.html)を参照してください。（→ 第9章）

**CASCADE**
: 親が消えたら子も連鎖的に消す設定です。`ON DELETE CASCADE` を付けると、ToDo を消したときに関連する `todo_tags` も自動で消えます。
  付けないと、親を消しても子だけが残る「孤立データ」が発生します。（→ 第4章）

**正規化**
: データの重複や矛盾が起きにくいように、テーブルをルールに沿って分割していく設計手法です。
  入門としては「同じ事実は 1 か所にだけ書く」の 1 文で十分です。
  重複を放置すると、更新時に一部だけ直し忘れてデータ不整合が起きやすくなります。（→ 第9章）

**ER 図**
: Entity-Relationship Diagram。テーブル間の関係を図示したものです。
  テーブルを作る前に関係性を図で確認しておくと、あとからの手戻りを減らせます。（→ 第9章）

**多対多 / 中間テーブル（JOIN テーブル）**
: 「1 つの ToDo に複数のタグ、1 つのタグを複数の ToDo に付けられる」のような関係を多対多と呼びます。
  リレーショナル DB では、対応関係だけを記録する中間テーブル（`todo_tags`）で表すのが定石です。（→ 第11章）

**JOIN**
: 複数テーブルを結合して 1 つの結果にする操作です。`INNER` / `LEFT` / `RIGHT` / `FULL OUTER` などの種類があります。
  正規化でテーブルを分けた分だけ、必要なときに JOIN で結果をまとめ直します。
  詳しくは[公式ドキュメント](https://www.postgresql.org/docs/current/queries-table-expressions.html)を参照してください。（→ 第4章）

**UPSERT（`INSERT ... ON CONFLICT`）**
: 「INSERT しつつ、重複時は UPDATE したり無視したりする」書き方の総称です（UPDATE + INSERT）。
  PostgreSQL の `INSERT ... ON CONFLICT DO NOTHING` は「UNIQUE 制約にぶつかったらエラーにせず無視する」という 1 文で、
  存在確認と挿入の間に別リクエストが割り込む競合（check-then-act の隙間）を防げます。（→ 第11章）

**LIMIT / OFFSET**
: SQL の取得行数制限と、何行目から取るかの指定です。ページングの基礎になります。
  本文の章では扱わず、構文は付録Aにまとめています。（→ 付録A「SQLチートシート」）

**インデックス**
: SQL の検索を速くするためのデータ構造で、`CREATE INDEX` で作ります。
  WHERE と ORDER BY の組み合わせに合わせて貼ると効果があります。
  詳しくは[公式ドキュメント](https://www.postgresql.org/docs/current/indexes.html)を参照してください。（→ 第9章）

**SERIAL**
: PostgreSQL の自動採番カラムを作るショートカットです。実体は `INTEGER` + シーケンスです。
  主キーの値を自分で採番・管理する手間をなくせます。（→ 第3章）

**TIMESTAMPTZ**
: タイムゾーン付きのタイムスタンプ型です。複数地域で使う可能性があるなら基本はこれを選びます。（→ 第3章）

**View（ビュー）**
: SELECT の結果に名前を付けたものです。実体のデータは持たず、参照のたびに計算されます。
  よく使う複雑な問い合わせに名前を付けて使い回せます。本研修では使わず、付録Aでも名前の紹介のみです。

**Trigger（トリガー）**
: テーブルに対する INSERT / UPDATE / DELETE をきっかけに自動実行される SQL です。
  ルールを DB 側に隠さずアプリのコードで見える形にしておきたいため、本研修ではあえて使いません。

**WAL**
: Write-Ahead Log。PostgreSQL の耐久性を支える「先にログを書く、本体はあとから」という仕組みです。
  本研修では深追いしません。

**N+1 問題**
: 1 件取ったあと、関連する子を 1 件ごとに別クエリで取ってしまう典型的な性能問題です。
  `IN` / `ANY` でまとめて取ると解消できます。（→ 第10章）

## トランザクション

**トランザクション**
: 複数の SQL を「ぜんぶ成功」か「ぜんぶ取り消し」のどちらかにまとめる仕組みです。
  `BEGIN; ... COMMIT;` または `ROLLBACK;` で使います。
  詳しくは[公式ドキュメント](https://www.postgresql.org/docs/current/tutorial-transactions.html)を参照してください。（→ 第4章）

**ACID**
: トランザクションが持つ 4 つの性質の頭文字です。
  原子性（Atomicity）・一貫性（Consistency）・独立性（Isolation）・永続性（Durability）の 4 つで、
  研修で主に実感するのは原子性です。（→ 第4章）

**コミット（COMMIT）/ ロールバック（ROLLBACK）**
: コミットはトランザクションの中で行った変更の確定、ロールバックは全部なかったことにする取り消しです。
  psycopg では自動でトランザクションが始まり、確定・取消のタイミングを Python 側で制御します。
  処理の途中でエラーが起きたときに中途半端な状態が残るのを防ぐのがロールバックの役目です。（→ 第4章、第6章、第12章）

**autocommit（自動コミット）**
: SQL を 1 文実行するたびに自動でコミットするモードです。
  psycopg では `autocommit=False` がデフォルトで、明示的に `commit()` するまで変更が確定しないため、
  複数の SQL をまとめてトランザクションにできます。`psycopg.connect(DSN, autocommit=True)` で切り替えられます。（→ 第6章）

## Python から DB へ

**クライアント / サーバー**
: サービスを提供し続ける側（サーバー）と、接続して要求を送る側（クライアント）に分ける考え方です。
  PostgreSQL はサーバーとして動き続け、psql や Python スクリプトはクライアントとして接続します。
  Web ではブラウザがクライアント、uvicorn で動かすアプリがサーバーです。（→ 第5章、第8章）

**ドライバ**
: アプリケーションと DB の間で会話を取り持つライブラリです。
  PostgreSQL はネットワーク越しに独自のプロトコルでやり取りするため、言語ごとのドライバが必要です。
  本研修では PostgreSQL 用ドライバの psycopg（バージョン 3）を使います。（→ 第5章）

**psycopg**
: Python から PostgreSQL を扱うドライバです。本研修ではバージョン 3 を使います。
  詳しくは[公式ドキュメント](https://www.psycopg.org/psycopg3/docs/)を参照してください。（→ 第5章〜第7章）

**コネクション / カーソル**
: コネクションは PostgreSQL サーバーとの通信路そのもの、カーソルはその上に作る「SQL を送って結果を受け取る窓口」です。
  コネクションが電話回線、カーソルがその電話で交わすひとつひとつの会話、という関係です。（→ 第5章）

**DSN（Data Source Name）**
: 接続に必要な情報を 1 本の文字列にまとめたものです。`host=localhost port=5432 dbname=tododb ...` の形で書きます。
  1 か所にまとまっていると、設定ファイルや環境変数に切り出しやすくなります。
  第10章では環境変数から読んだ設定値をもとに DSN を組み立てます。（→ 第5章、第10章）

**コネクションプール**
: 接続を使うたびに新しく作るのではなく、あらかじめ何本か作っておいて使い回す仕組みです。
  接続の確立（TCP 接続・認証・バックエンドプロセスの起動）は重い処理なので、
  リクエストごとに DB アクセスが発生する Web アプリでは必須の仕組みです。（→ 第7章）

**バインディング / プレースホルダ**
: 値を SQL に直接連結せず、`%s`（psycopg）や `?`（一部のドライバ）で書いて値を別に渡す方式です。
  SQL インジェクション対策の基本です。（→ 第6章）

**マイグレーション**
: DB のスキーマ（テーブル定義）の作成・変更を連番付きの SQL ファイルとして残し、順番に適用していくやり方です。
  変更履歴が Git に残り、新しい環境でもファイルを番号順に流し込むだけで同じスキーマを再現できます。
  実務では Alembic や Flyway などの専用ツールを使います。（→ 第9章）

**ORM**
: Object-Relational Mapper。SQL を書かずにオブジェクト操作で DB を扱う仕組みです。
  実務では SQL を書く手間を減らす目的でよく使われますが、本研修では SQL そのものの理解を優先するためあえて使いません。（→ index、第14章）

**レイヤー分け**
: Web アプリのコードを役割ごとのファイル（層）に分けて書く定石です。
  本研修ではルーター・サービス・リポジトリ・モデル・DB 接続に分けます。
  変更が起きたときに直す場所がどこか即座にわかるようにするのが目的です。（→ 第10章）

**Repository パターン**
: 「DB アクセスをまとめる層」を作って、他の層から SQL を直接呼ばない設計です。
  SQL が散らばらないので、テストの際に DB アクセス部分だけ差し替えやすくなります。（→ 第10章）

**ドメインモデル**
: アプリ内で扱う「もの」を表す型のことです。本研修では dataclass で表現します。
  DB の行（文字列キーの辞書）をすぐドメインモデルに詰め替えると、属性アクセスになり型ヒントの恩恵を受けられます。（→ 第10章）

## Web と HTTP

**HTTP**
: Web の通信プロトコルです。クライアントが送るリクエスト（メソッド + URL + クエリパラメータ + ボディ）と、
  サーバーが返すレスポンス（ステータスコード + ボディ）の往復で成り立ちます。
  ブラウザも API クライアントも同じ土台の上で通信できる、Web 共通のルールです。
  詳しくは[公式ドキュメント](https://developer.mozilla.org/ja/docs/Web/HTTP/Methods)を参照してください。（→ 第8章）

**HTTP メソッド**
: リクエストが「何をしたいか」を表す部分です。
  `GET`（取得）、`POST`（作成）、`PATCH`（部分更新）、`PUT`（丸ごと差し替え）、`DELETE`（削除）などがあります。
  一部の項目だけ変えたい場面のために PATCH と PUT が使い分けられます。（→ 第8章、第14章）

**ステータスコード**
: レスポンスの結果の種別を表す 3 桁の数字です。
  成功系は `200 OK`、`201 Created`、`204 No Content`、失敗系は `404 Not Found`（対象が存在しない）、
  `422 Unprocessable Content`（値が制約を満たさない）などが研修で登場します。（→ 第8章、第14章）

**冪等性（べきとうせい）**
: 「同じリクエストを 1 回投げても 2 回投げても、結果が変わらない」という性質です。
  `GET` / `PUT` / `DELETE` は基本的に冪等ですが、`POST /api/todos` は呼ぶたびに ToDo が増えるので冪等ではありません。
  通信エラー時にリトライしてよいかどうかを考える目安になります。（→ 第8章）

**API（Application Programming Interface）**
: プログラムの境界です。本研修では「HTTP で呼ばれるサーバー側の窓口」を指します。`/api/todos` がそれです。（→ 第13章）

**REST**
: Web の API を設計するときの代表的な考え方です。
  「URL は『何のデータか』を指す名詞にする」「『何をするか』は HTTP メソッドで表す」という 2 点が中心のルールで、
  URL をリソースの住所に徹します。（→ 第8章）

**CRUD**
: Create / Read / Update / Delete。データに対する 4 つの基本操作です。
  多くの操作をこの 4 種類に当てはめて考えられるので、API 設計や画面設計の見通しを立てやすくなります。
  第8章で設計し、第14章で API として実装します。（→ 第8章、第14章）

## Web アプリの構成要素

**ASGI / WSGI**
: Python の Web フレームワークと Web サーバーの間の取り決め（インタフェース）です。
  FastAPI で作ったアプリは ASGI アプリという形をしていて、ASGI に対応したサーバーなら何でも動かせます。
  ASGI は非同期処理を前提にしているため、WSGI（Flask など）では苦手だった同時接続の多い処理に強いです。（→ 第13章）

**uvicorn**
: 実際にポートを開いて HTTP リクエストを受け付け、FastAPI アプリに渡す実行エンジン（ASGI サーバー）です。
  `uvicorn app.main:app` は「`app/main.py` の中の `app` という変数（ASGI アプリ）を動かしてくれ」という指定です。（→ 第13章）

**FastAPI**
: Python の Web フレームワークで、「どの URL にどのメソッドで来たらどの関数を呼ぶか」を定義します。
  型ヒントから入力チェックや API ドキュメントが自動生成されるのが特徴です。
  詳しくは[公式ドキュメント](https://fastapi.tiangolo.com/)を参照してください。（→ 第13章）

**Pydantic**
: 型ヒントベースのバリデーションライブラリです。バリデーションのルールを型として書けます。
  FastAPI と組み合わせることで、不正なリクエストを処理の奥に入れる前に入口で自動的に弾けます。
  詳しくは[公式ドキュメント](https://docs.pydantic.dev/latest/)を参照してください。（→ 第13章、第14章）

**OpenAPI / Swagger UI**
: OpenAPI は API の仕様を機械可読な JSON で表したもの、Swagger UI はそれを描画した画面です。
  FastAPI は型ヒントから OpenAPI スキーマを自動生成し、`/docs` で Swagger UI を最初から提供します。（→ 第13章）

**依存性注入（DI）**
: 「関数が必要とするものを関数の中で自分で組み立てる」のではなく、「外側（フレームワーク）が用意して引数に差し込んでくれる」設計パターンです。
  pytest のフィクスチャとほぼ同じ考え方で、FastAPI ではエンドポイント関数の引数に「`conn` が欲しい」と書くと接続が渡されます。
  各関数は接続の作り方を知らなくて済み、作り方を変えたいときは差し込む側だけ直せばよくなります。（→ 第13章）

**サーバーサイドレンダリング（SSR）**
: サーバーが HTML を完成させてから返す方式です。ブラウザは届いた HTML を表示するだけで済みます。
  JSON だけを返してブラウザ側の JavaScript が画面を組み立てる SPA（React / Vue など）と対照的な方式です。（→ 第15章）

**テンプレートエンジン / Jinja2**
: 「見た目は HTML のまま書きつつ、動的な部分だけを差し込む」ための仕組みです。
  Python 製の Jinja2 は `{{ ... }}`（値の出力）と `{% ... %}`（`for` や `if` の制御構文）の 2 種類の記法を HTML に埋め込めます。
  `{{ ... }}` の値は自動で HTML エスケープされるので、XSS 対策も最初から有効です。（→ 第15章）

**Ajax / 部分更新**
: ページ全体を読み直さず、サーバーから変わった部分のデータだけを受け取ってブラウザ上で書き換える仕組みです。
  通信量が減るだけでなく、スクロール位置や入力途中の値が保たれ、画面のチラつきも起きません。（→ 第16章）

**htmx**
: Ajax の挙動を HTML の属性（`hx-get`、`hx-target` など）として宣言するための小さな JavaScript ライブラリです。
  サーバーは HTML を返すだけでよく、JavaScript をほとんど書かずに動的な UI を作れます。
  詳しくは[公式ドキュメント](https://htmx.org/docs/)を参照してください。（→ 第16章）

**HTML フラグメント**
: `<!doctype html>` から始まる完全な HTML 文書ではなく、`<table>...</table>` のようなページの一部分だけを切り出した HTML です。
  htmx は返ってきた断片をそのまま `hx-target` の場所に差し込みます。（→ 第16章）

## セキュリティ

**SQL インジェクション**
: 入力フォームなどから渡された「値」に SQL の命令を紛れ込ませる攻撃です。
  値を SQL 文字列に連結しない（プレースホルダを必ず使う）ことで防げます。（→ 第6章）

**XSS（クロスサイトスクリプティング）/ エスケープ**
: 悪意のある入力に埋め込まれた `<script>` タグがそのままブラウザで実行されてしまう脆弱性です。
  Jinja2 は `{{ ... }}` の出力を自動で HTML エスケープ（`<` を `&lt;` に変換するなど）するので、
  `{{ value | safe }}` をユーザー入力に安易に使わない限り安全です。
  詳しくは[公式ドキュメント](https://developer.mozilla.org/ja/docs/Web/Security/Attacks/XSS)を参照してください。（→ 第15章）

**CSRF（クロスサイトリクエストフォージェリ）**
: ログイン中のユーザーをだまして、本人の意図しない操作（送金など）を実行させる攻撃です。
  本研修では扱いません。詳しくは[公式ドキュメント](https://developer.mozilla.org/ja/docs/Web/Security/Attacks/CSRF)を参照してください。

## 運用とデプロイ

**環境変数**
: OS がプロセスに渡す名前つきの値の仕組みです。プログラムの外側から値を差し込めるので、コードを書き換えずに動作を変えられます。
  環境ごとの設定切り替えと、パスワードなどの秘密情報をコード（Git）に書かないために使います。（→ 第17章）

**ログ**
: プログラムが「いつ・何が起きたか」を残す記録です。
  Python 標準の `logging` を使うと、DEBUG / INFO / WARNING / ERROR / CRITICAL の重要度（レベル）を付けて
  「このレベル以上だけ出す」を設定 1 つで切り替えられます。（→ 第17章）

**例外ハンドリング**
: 想定したエラー（404 や 422）は個別に返し、想定外の例外はアプリ全体で 1 箇所に集約して、
  応答は JSON の定型文にそろえ、スタックトレースはサーバー側のログに確実に残す、という方針のことです。（→ 第17章）

**デプロイ**
: 開発していたアプリを、実際に使ってもらう環境（本番環境）に置いて動かすことです。
  開発用の便利機能（`--reload` など）を外し、安定して動き続ける形で起動します。（→ 第18章）

**PaaS / VPS / コンテナ基盤**
: 本番環境の置き場所の 3 系統です。PaaS（Render、Fly.io など）はサービス側が面倒をみてくれて初心者向き、
  VPS（さくら、Vultr など）は VM を借りて全部自分でやる代わりに自由、
  コンテナ基盤は Dockerfile のイメージをそのまま実行環境に載せる形です。（→ 第18章）
