# 第18章 公開先と最終課題

研修の最終章です。
**どこに置くか**の選択肢と、研修全体を踏まえた **総仕上げの課題**を扱います。

## 18.1 公開先の選択肢

「自分だけが触る」のか「インターネットに出す」のかで、選ぶ場所が変わります。

| 用途 | 候補 | 一言 |
|---|---|---|
| 自分の PC だけ | そのまま `uvicorn` | 一番気楽 |
| 家庭内 LAN | `--host 0.0.0.0` で起動 | 同じ Wi-Fi の端末から触れる |
| 個人で軽く外に出したい | [Fly.io](https://fly.io/) / [Render](https://render.com/) | 無料枠あり |
| 自由度が欲しい | VPS（さくら / Vultr / DigitalOcean） | ssh と nginx の知識が要る |
| 仕事で使う | クラウド（AWS / GCP / Azure） | 本研修の範囲外 |

!!! note "選択肢を丸暗記しない：何が変わるか"
    表の右に行くほど**自由度は上がるが、自分で面倒を見る範囲も増えます**。Fly.io や Render の
    ような PaaS（Platform as a Service）は、OS のアップデートや証明書の更新をサービス側が
    代行してくれる代わりに、決められた枠組みの中で動かすことになります。VPS はその逆で、
    サーバーの中身を全部自分で面倒みる代わりに何でも自由にできます。まずは PaaS で慣れて、
    必要になったら VPS やクラウドへ、という順番がおすすめです。

外に出す場合は最低限:

1. **HTTPS** にする（[Caddy](https://caddyserver.com/) なら自動）
2. **PostgreSQL は別ホスト**にする（同じコンテナで永続化しない）
3. **バックアップを取る**（`pg_dump` を cron で）
4. **環境変数を本番値に差し替える**（`DB_PASSWORD` など）

!!! note "なぜ HTTPS が実質必須なのか"
    HTTP は通信内容が平文のまま流れるため、途中の経路で**盗聴**（パスワードや Cookie を
    覗き見される）や**改ざん**（内容を書き換えられる）が起こり得ます。HTTPS はこの通信を
    暗号化し、証明書によって接続先が本物かどうかも確認できるようにする仕組みです。
    ログインやフォーム入力があるアプリを外に出すなら、事実上必須と考えてください。

!!! note "なぜ PostgreSQL をアプリと同居させないのか"
    アプリと DB を同じコンテナにまとめると、アプリを作り直したり再デプロイしたりするたびに
    中のデータが消えるおそれがあります（**永続化**の問題）。また、アクセス増加に応じて
    アプリだけを複数台に増やしたい（**スケーリング**）場合や、アプリ側の不具合が DB を
    巻き込まないようにしたい（**障害分離**）場合にも、コンテナを分けて DB 専用のボリューム・
    ホストに置いておくほうが安全です。

!!! note "バックアップがなぜ要るか"
    ディスク障害、操作ミス（`WHERE` を忘れた `DELETE` など）、災害といった理由で、
    DB のデータはある日突然失われることがあります。バックアップは「何かあっても、この時点まで
    戻せる」という保険です。`pg_dump` は PostgreSQL 標準のバックアップコマンドで、詳細は
    [PostgreSQL公式ドキュメント](https://www.postgresql.org/docs/current/) を参照してください。

!!! note "本番で環境変数を差し替える理由"
    開発中のパスワードや接続先をそのまま外部に公開すると、認証情報が漏れたり、開発用の
    緩い設定が本番でも有効になったりする危険があります。設定をコードに直接書かず環境変数として
    外から与えるようにしておけば、環境（開発／本番）ごとに値を差し替えるだけで安全に切り替えられます。

## 18.2 LAN 公開の試し方

ちょっと触る程度なら、まず家庭内 LAN で十分です。

```bash
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

`--host 0.0.0.0` は「どのネットワークインターフェースからの接続でも受け付ける」という指定です。
何も指定しないとデフォルトの `127.0.0.1`（自分自身からしか繋げないアドレス）で待ち受けるため、
他の端末からアクセスするにはこの指定が必要になります。

スマホで `http://<PCのローカルIP>:8000/` を開くと触れます。
PC の IP アドレスは:

```bash
# Linux / macOS
ip addr show | grep inet
# Windows (PowerShell)
ipconfig
```

！ ファイアウォールでブロックされていることがあります。
研修目的なら一時的に通してもいいですが、**作業が終わったら戻す**こと。

## 18.3 簡単なコンテナ化（参考）

将来 Fly.io などにデプロイする想定なら、Dockerfile を作っておくのが便利です。
（研修必須ではありません）

```dockerfile
# Dockerfile（例）
FROM python:3.12-slim

ENV UV_LINK_MODE=copy
RUN pip install uv

WORKDIR /app
COPY pyproject.toml uv.lock* ./
RUN uv sync --frozen --no-dev

COPY app ./app
COPY migrations ./migrations

EXPOSE 8000
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

それぞれの命令がざっくり何をしているかも見ておきましょう。

- **`FROM`**: ベースにするイメージを指定します。ここでは Python 3.12 の軽量イメージを使い、
  OS やインタプリタをゼロから用意する手間を省いています。
- **`WORKDIR`**: これ以降のコマンドを実行する作業ディレクトリを指定します（なければ作られます）。
- **`COPY`**: ホスト側のファイルをイメージの中にコピーします。依存関係のファイル
  （`pyproject.toml` / `uv.lock`）だけ先にコピーしてインストールしてから、あとでアプリの
  コード（`app` / `migrations`）をコピーしているのは、コードだけを直したときに依存関係の
  インストールをやり直さずに済む（ビルドのキャッシュを活かせる）ようにするためです。
- **`RUN`**: イメージを作る時点で 1 回だけ実行するコマンドです（依存パッケージのインストールなど）。
- **`EXPOSE`**: コンテナがどのポートで待ち受けるかを示す**ドキュメント的な**命令です。これを
  書いただけではポートが外部に開放されるわけではなく、実際に開放するのは `docker run -p` や
  Docker Compose の `ports` 設定側です。
- **`CMD`**: コンテナを起動したときに実行されるデフォルトのコマンドです。

各命令の詳しい仕様は [Dockerfileリファレンス](https://docs.docker.com/reference/dockerfile/)
にまとまっています。

## 18.4 動作確認チェックリスト

完成形を平井さんに渡すときに、このチェックを通しておくと安心です。

- [ ] `docker compose up -d` で DB が起動する
- [ ] `uv run python -m app.cli init-db` でテーブルが作られる
- [ ] `uv run uvicorn app.main:app --reload` で起動する
- [ ] `http://127.0.0.1:8000/` でリストが見える
- [ ] 追加・完了切替・削除がそれぞれ動く
- [ ] フィルタ（全/未/完）と検索が動く
- [ ] `http://127.0.0.1:8000/docs` で Swagger UI が表示される
- [ ] `uv run pytest -v` がぜんぶ緑

## 18.5 これから先のお題

研修としてはここまでですが、続けるなら次のテーマがおすすめです。

1. **複数ユーザー対応**: **認証**（ログインなどで「誰か」を確かめる仕組み）・**認可**（その人が
   何をしてよいかを決める仕組み。他人の ToDo は操作できない、など）、ToDo を所有するユーザー、
   **CSRF 対策**（ログイン中のユーザーになりすまして意図しない操作をさせる攻撃を防ぐ仕組み。
   [MDN: CSRF](https://developer.mozilla.org/ja/docs/Web/Security/Attacks/CSRF) 参照）
2. **マイグレーションの本格化**: Alembic を導入する
3. **コネクションプールの本気運用**: 監視（接続数・スロークエリ）、再接続
4. **CI**: [GitHub Actions](https://docs.github.com/en/actions)（コードを push するたびに
   テストや静的解析を自動で走らせる仕組み）で `pytest` と `ruff` を回す
5. **デプロイ**: Fly.io か Render に上げて URL を共有してみる
6. **観測**: 構造化ログ（JSON）と Sentry のエラー送信
7. **大量データへの耐性**: 100 万件入れてみて、
   [`EXPLAIN ANALYZE`](https://www.postgresql.org/docs/current/sql-explain.html) で見直す

## 18.6 最終課題

研修の総仕上げです。
ここまで覚えた範囲で、**「自分が欲しい機能」を 1 つだけ追加** してみてください。

たとえば:

- ToDo に **メモ（複数行）** を持たせる
- ToDo を **CSV にエクスポート**する画面を付ける
- **完了済みは別タブ** に隠す
- **期限が今日のもの**にバッジを付ける
- **タグ別の件数**をフッタに表示

進め方の目安:

1. **設計**: テーブル変更が要るか、API はどうなるか、画面はどう見えるか
2. **マイグレーション**: 必要なら `migrations/00X_xxx.sql` を追加して `init-db`
3. **リポジトリ**: SQL を書いて、テストを書く
4. **API**: スキーマを更新して、ルーターに足し、テストを書く
5. **画面**: テンプレートと CSS を更新する
6. **動作確認**: チェックリストを通す

「**薄く 1 周**」すれば、研修で扱った内容のほとんどを使うはずです。
余裕があれば、**コミットを機能ごとに分けて、PR の説明文を書く**ところまでやると、
そのまま実務の流れになります。
