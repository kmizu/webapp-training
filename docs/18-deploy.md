# 第18章 公開先と最終課題

研修の最終章です。第17章までで ToDo アプリは完成しましたが、
いまの動かし方は「自分の PC で開発するためのもの」です。
この章では、作ったアプリを**本番として動かす**とはどういうことかを学び、
手元で再現できる形で試します。後半は、研修全体の総仕上げとして
**最終課題**に取り組みます。

## 18.1 この章でやること

この章が終わったときに、次のことができる状態を目指します。

- デプロイとは何か、公開先の選択肢（PaaS / VPS / コンテナ）の違いを
  説明できる
- 開発用と本番用の起動コマンドの違いを説明し、**本番相当の起動**を
  手元で再現できる
- 本番では環境変数を `.env` ファイルではなく環境の仕組みで渡す理由を
  説明し、実際に渡して起動できる
- Dockerfile を書き、アプリをコンテナイメージにまとめて起動できる
- 最終課題に、段階的な手順に沿って取り組める

**所要時間の目安: 60 分**（最終課題は別途、じっくり取り組んでください）

!!! info "前提となる状態"
    - 第17章末時点の `mytodo/` がある（全ファイルが完成版と一致し、
      ログ・`.env`・例外ハンドラまで入った状態）
    - 第0章の Docker の PostgreSQL が起動している
      （`docker compose up -d`）
    - シードデータが入った状態である

## 18.2 前提知識

コードに入る前に、この章の鍵になる概念を押さえておきます。

!!! note "デプロイとは"
    **デプロイ**は、「開発していたアプリを、実際に使ってもらう環境
    （本番環境）に置いて動かすこと」です。これまでの章でやってきた
    `uv run uvicorn ... --reload` での起動も広い意味ではアプリを
    動かしていますが、あれは**開発用**の動かし方です。本番では、
    開発のための便利機能を外し、**安定して動き続ける形**で起動します。
    この章ではその違いを、実際に手を動かして確認します。

!!! note "公開先の選択肢: PaaS / VPS / コンテナ"
    本番環境の置き場所には、大きく 3 つの系統があります。

    - **PaaS**（Platform as a Service。[Render](https://render.com/) や
      [Fly.io](https://fly.io/) など）…… アプリのコード（または
      コンテナイメージ）を渡すと、OS の更新や証明書の管理をサービス側が
      面倒みてくれます。自由度は低めですが、はじめての公開には
      一番向いています。
    - **VPS**（Virtual Private Server。さくら / Vultr / DigitalOcean
      など）…… 仮想的なサーバーを 1 台借りる形です。ssh でログインし、
      OS の更新からミドルウェアの設定まですべて自分でやる代わりに、
      何でも自由にできます。
    - **コンテナ基盤**（クラウドのコンテナ実行サービスや Kubernetes
      など）…… Dockerfile で作ったコンテナイメージをそのまま実行
      環境に載せる形です。18.6 で作るイメージがそのまま使えますが、
      本格的な運用は本研修の範囲外です。

    右に行くほど自由度は上がりますが、自分で面倒を見る範囲も増えます。
    まずは PaaS で慣れて、必要になったら VPS やコンテナ基盤へ、という
    順番がおすすめです。

!!! note "開発用と本番用で、なぜ起動方法が違うのか"
    開発用の起動に付けていた `--reload` は、ファイルの変更を監視して
    プロセスを自動で再起動する**開発専用の仕組み**です。第17章で確認した
    とおり、本番では無駄な監視のオーバーヘッドと意図しない再起動のもとに
    なるため外します。また開発では `--env-file .env` で設定をファイルから
    読んでいましたが、本番では `.env` ファイルをサーバーに置かず、
    **環境変数を環境側の仕組みで渡す**のが定石です（18.4 で実際に
    やります）。

## 18.3 開発用と本番用の起動コマンド

まず、2 つの起動方法を並べて整理します。

| | 開発用 | 本番用 |
|---|---|---|
| コマンド | `uv run uvicorn app.main:app --reload --env-file .env` | `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| 待ち受けるアドレス | `127.0.0.1`（自分の PC だけ） | `0.0.0.0`（外部からの接続も受け付ける） |
| 設定の渡し方 | `.env` ファイル（`--env-file`） | 環境変数を環境側の仕組みで設定 |
| 自動再起動 | あり（`--reload`） | なし |

`--host 0.0.0.0` は「どのネットワークインターフェースからの接続でも
受け付ける」という指定です。何も指定しないとデフォルトの `127.0.0.1`
（自分自身からしか繋げないアドレス）で待ち受けるため、他の端末や
コンテナの外からアクセスするにはこの指定が必要になります。

### 本番相当の起動を手元で試す

`mytodo/` の中で、**`--reload` と `--env-file` を外して**起動して
みましょう。

```bash
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

期待される出力（プロセス番号は環境によって変わります）:

```text
INFO:     Started server process [12345]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

`http://0.0.0.0:8000` と表示され、`--env-file` を付けていないので
先頭に `Loading environment from ...` の行が**出ない**のが開発用との
違いです。`config.py` のデフォルト値（第0章の Docker の PostgreSQL に
合わせた練習用の値）がそのまま使われるので、研修環境ではこのまま
動きます。

**別のターミナル**を開いて、次の curl を実行してください。

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:8000/api/todos
```

期待される出力:

```text
HTTP 200
```

uvicorn 側のターミナルには、第17章で追加したリクエストログが本番相当の
起動でも出ています。

期待される出力（uvicorn 側のターミナル。時刻は実行ごとに変わります）:

```text
2026-08-16 09:23:41,792 INFO todo-app - GET /api/todos -> 200
```

確認できたら `Ctrl+C` で止めてください。

第17章で入れた仕組みが本番でどう活きるか、ここで一度整理して
おきます。

- **ログ** …… 本番では、サーバーを止めずに原因を調べる唯一の手がかりが
  ログです。リクエストログと例外時のスタックトレースが、起動方法が
  変わっても同じ形式で出続けます。
- **例外ハンドラ** …… 本番で想定外の例外が起きても、応答は JSON の
  定型文にそろいます。利用者に余計な内部情報が見えず、呼び出し側の
  エラー処理も 1 通りで済みます。
- **`.env` と環境変数** …… 設定をコードから分離してあるので、本番用の
  値に差し替えるのは環境変数の渡し方を変えるだけです。次の 18.4 で
  本番流の渡し方を試します。

## 18.4 本番では環境変数を環境の仕組みで渡す

`.env` ファイルは開発用の便利な受け皿でしたが、本番のサーバーには
置きません。理由は 2 つあります。1 つは、秘密情報の書かれたファイルを
サーバー上で管理する（置き場所・権限・更新のたびの配布）のは事故の
もとだからです。もう 1 つは、PaaS やコンテナ基盤には「環境変数を
設定する仕組み」が最初から備わっていて、そちらに載せるほうが安全だ
からです。

手元でその流れを再現できます。コマンドの先頭に `名前=値` を並べると、
そのプロセスだけに環境変数を渡せます（第17章の問2 で `LOG_LEVEL` に
対してやったのと同じ形です）。`mytodo/` の中で実行してください。

```bash
DB_HOST=localhost DB_PORT=5432 DB_NAME=tododb DB_USER=todo DB_PASSWORD=todo \
  uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

期待される出力（先頭付近）:

```text
INFO:     Started server process [12345]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

いま渡した値はデフォルトと同じなので動作は変わりませんが、
**`.env` ファイルを一切使わずに設定を注入できている**のがポイント
です。本番ならここに本番用の `DB_HOST` や `DB_PASSWORD` を渡します。
コードは一行も変えません。

別のターミナルで次を実行し、`HTTP 200` になることを確認したら、
uvicorn 側のターミナルで `Ctrl+C` を押して止めてください。

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:8000/api/todos
```

期待される出力:

```text
HTTP 200
```

!!! warning "シェルの履歴にパスワードが残る"
    練習ではコマンドの先頭に書きましたが、この形はシェルの履歴
    （`history` コマンドで見えるもの）に値が残ります。実務では PaaS の
    設定画面や `docker run -e`（18.6）、シークレット管理の仕組みから
    渡すので、コマンドに直接書くのはあくまで練習用の簡易版です。

## 18.5 LAN で公開してみる

「本番」といっても、まずは家庭やオフィスの LAN で試すのが手軽です。
18.3 の起動はすでに `--host 0.0.0.0` 付きなので、あとは自分の PC の
IP アドレスを調べるだけです。

```bash
# Linux / macOS
ip addr show | grep inet
# Windows (PowerShell)
ipconfig
```

期待される出力（Linux の例。`192.168.x.x` のようなアドレスが
見つかります）:

```text
    inet 127.0.0.1/8 scope host lo
    inet 192.168.1.10/24 ... scope global ...
```

サーバーを `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` で
起動したまま、同じ Wi-Fi に繋いだスマホや別の PC で
`http://192.168.1.10:8000/`（自分のマシンのアドレスに読み替えて
ください）を開くと、ToDo の画面が見えるはずです。

!!! warning "ファイアウォールに注意"
    ファイアウォールでブロックされていることがあります。研修目的で
    一時的に許可することはありますが、**試し終わったら必ず元に戻して
    ください**。また、LAN 公開はあくまで同じネットワーク内の相手向けで、
    インターネットへの公開とは別物です（18.7 参照）。

## 18.6 Dockerfile でコンテナ化する

PaaS やコンテナ基盤に載せるには、アプリを**コンテナイメージ**に
まとめます。第0章で PostgreSQL をコンテナで動かしたのと同じ仕組みを、
今度は自分のアプリに適用します。イメージにしておくと、「手元の
`.venv` と本番で環境が微妙に違う」という再現性の問題をまるごと
消せます。ベースイメージで Python のバージョンを固定し、`uv.lock` で
依存パッケージを固定するのが、そのための 2 つの柱です。

`mytodo/Dockerfile` を作成して、次の内容を書き写してください。

```dockerfile
# Dockerfile
FROM python:3.12-slim

ENV UV_LINK_MODE=copy
RUN pip install uv

WORKDIR /app
COPY pyproject.toml uv.lock* ./
RUN uv sync --frozen --no-dev

COPY app ./app
COPY migrations ./migrations

EXPOSE 8000
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

それぞれの命令がざっくり何をしているかも見ておきましょう。

- **`FROM`**: ベースにするイメージを指定します。ここでは Python 3.12 の
  軽量イメージを使い、OS やインタプリタをゼロから用意する手間を省いて
  います。`3.12` と minor バージョンまで指定することで、手元と同じ
  Python 系で動かせます。
- **`RUN pip install uv`**: イメージの中に uv をインストールします。
  教材では簡単のためバージョンは未固定ですが、実務では
  `pip install uv==<バージョン>` のように固定すると再現性がさらに
  上がります。
- **`WORKDIR`**: これ以降のコマンドを実行する作業ディレクトリを指定
  します（なければ作られます）。
- **`COPY`**: ホスト側のファイルをイメージの中にコピーします。依存関係の
  ファイル（`pyproject.toml` / `uv.lock`）だけ先にコピーしてインストール
  してから、あとでアプリのコード（`app` / `migrations`）をコピーして
  いるのは、コードだけを直したときに依存関係のインストールをやり直さず
  に済む（ビルドのキャッシュを活かせる）ようにするためです。
- **`RUN uv sync --frozen --no-dev`**: `uv.lock` どおりに依存パッケージを
  インストールします。`--frozen` は「ロックファイルとずれていたら
  エラーにする」指定で、再現性の要です。`--no-dev` で pytest などの
  開発用パッケージはイメージに入れません。
- **`EXPOSE`**: コンテナがどのポートで待ち受けるかを示す
  **ドキュメント的な**命令です。これを書いただけではポートが外部に
  開放されるわけではなく、実際に開放するのは `docker run -p` 側です。
- **`CMD`**: コンテナを起動したときに実行されるデフォルトのコマンド
  です。`--reload` なし・`--host 0.0.0.0` 付きの**本番用の形**に
  なっていることを確認してください（コンテナの外からアクセスするので
  `0.0.0.0` が必須です）。

ここで、**`.env` を `COPY` していない**ことに注目してください。秘密情報を
イメージに焼き込むと、イメージを共有した相手全員に秘密が渡ってしまい
ます。設定はコンテナの起動時に環境変数で渡します。これが 18.4 の
「環境の仕組みで渡す」の実際の姿です。

各命令の詳しい仕様は
[Dockerfileリファレンス](https://docs.docker.com/reference/dockerfile/)
にまとまっています。

### イメージをビルドして起動する

`mytodo/` の中で、イメージをビルドします（初回はベースイメージの
ダウンロードに数分かかることがあります）。

```bash
docker build -t mytodo:0.1.0 .
```

期待される出力（末尾付近。所要時間やハッシュは環境によって変わります）:

```text
[+] Building xx.xs (13/13) FINISHED
 => => writing image sha256:...
 => => naming to docker.io/library/mytodo:0.1.0
```

`mytodo:0.1.0` は「イメージ名:タグ」です。タグでバージョンを区別します。

次にコンテナを起動します。ポイントは、第0章の DB コンテナと**同じ
Docker ネットワーク**に繋ぎ、環境変数は `-e` で渡すことです。

```bash
docker run --rm --network webapp-training_default \
  -e DB_HOST=webapp-training-db -e DB_PORT=5432 \
  -e DB_NAME=tododb -e DB_USER=todo -e DB_PASSWORD=todo \
  -p 8000:8000 mytodo:0.1.0
```

期待される出力（先頭付近）:

```text
INFO:     Started server process [1]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

オプションの意味:

- `--rm` …… コンテナが止まったら自動で削除する（試行錯誤でゴミが
  残らないようにするおまじないです）
- `--network webapp-training_default` …… 第0章の DB コンテナがいる
  ネットワークに接続します（この名前は `docker compose up -d` の出力に
  `Network webapp-training_default Created` とあったものです）。コンテナ
  の中からは、DB はコンテナ名の `webapp-training-db` というホスト名で
  見えます
- `-e 名前=値` …… 環境変数をコンテナに渡します。18.4 でコマンドの
  先頭に並べたものと同じ役割です
- `-p 8000:8000` …… ホストの 8000 番をコンテナの 8000 番に繋ぎます

別のターミナルで確認します。

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:8000/api/todos
```

期待される出力:

```text
HTTP 200
```

コンテナの中で動いたアプリが、手元の Docker の PostgreSQL に繋がって
応答しました。確認できたら、コンテナを動かしているターミナルで
`Ctrl+C` を押して止めてください（`--rm` 付きなのでコンテナは自動で
消えます）。

## 18.7 インターネットに公開するときの選択肢

「自分だけが触る」のか「インターネットに出す」のかで、選ぶ場所が
変わります。

| 用途 | 候補 | 一言 |
|---|---|---|
| 自分の PC だけ | そのまま `uvicorn` | 一番気楽 |
| 家庭内 LAN | 18.5 の手順 | 同じ Wi-Fi の端末から触れる |
| 個人で軽く外に出したい | [Fly.io](https://fly.io/) / [Render](https://render.com/) | 無料枠あり。18.6 のイメージが使える |
| 自由度が欲しい | VPS（さくら / Vultr / DigitalOcean） | ssh と nginx の知識が要る |
| 仕事で使う | クラウド（AWS / GCP / Azure） | 本研修の範囲外 |

外に出す場合は最低限、次の 4 点を押さえてください。

1. **HTTPS にする** …… HTTP は通信内容が平文で流れるため、途中の経路で
   盗聴や改ざんが起こり得ます。HTTPS は通信を暗号化し、証明書で接続先が
   本物かどうかも確認できるようにする仕組みです。ログインやフォーム入力が
   あるアプリを外に出すなら事実上必須です。PaaS なら自動で付くことが
   多く、自分でやるなら [Caddy](https://caddyserver.com/) が簡単です。
2. **PostgreSQL は別ホストにする** …… アプリと DB を同じコンテナに
   まとめると、アプリを再デプロイするたびにデータが消えるおそれが
   あります（永続化の問題）。アクセス増加に応じてアプリだけを複数台に
   増やす（スケーリング）ことも、アプリ側の不具合が DB を巻き込まない
   ようにする（障害分離）ことも難しくなります。DB は専用のホストや
   ボリュームに置きます。
3. **バックアップを取る** …… ディスク障害や操作ミス（`WHERE` を忘れた
   `DELETE` など）で、DB のデータはある日突然失われることがあります。
   `pg_dump`（PostgreSQL 標準のバックアップコマンド）を cron などで
   定期実行するのが基本です。詳細は
   [PostgreSQL公式ドキュメント](https://www.postgresql.org/docs/current/)
   を参照してください。
4. **環境変数を本番値に差し替える** …… 開発用の `todo / todo` のような
   練習用の値を本番で使いません。18.4 の仕組みで本番用の値を渡します。
   設定がコードから分離されているので、コードの変更は不要です。

- [ ] インターネットに公開する場合の最低限の 4 点（HTTPS、DB の分離、
      バックアップ、環境変数の差し替え）を理由つきで説明できる

## 18.9 つまずきポイント

### 本番相当で起動したら `/api/todos` が 500 になる

`--env-file .env` を外した起動では `.env` は読み込まれません。
`.env` にデフォルトと違う値を書いていた場合、その値が効かなくなり
ます。デフォルト値とも違う DB を指していると接続に失敗し、応答は
第17章のフォールバックハンドラが返す定型文になります。

```text
{"detail":"internal server error"}
```

このとき uvicorn 側のログには `ERROR todo-app - unhandled error:
GET /api/todos` に続いてスタックトレースが残っているはずです。
「本番で 500 が出たら、まず環境変数の渡し漏れや値の誤りを疑い、
ログを見る」という本番運用の基本を体験する良い機会です。
研修環境では、Docker の PostgreSQL が起動しているか
（`docker compose ps`）も確認してください。

### `docker build` の `uv sync --frozen --no-dev` でこける

`uv.lock` が `pyproject.toml` とずれていると `--frozen` が失敗します。
手元で `uv lock` を実行してロックファイルを更新してから、ビルドし直して
ください。また、`pyproject.toml` や `uv.lock` が `mytodo/` 直下にあるか
（`COPY` の取りこぼしがないか）も確認してください。

### コンテナから DB に繋がらない

`--network webapp-training_default` の付け忘れ、または
`DB_HOST=webapp-training-db` の指定漏れが典型です。ネットワーク名は
リポジトリのディレクトリ名に由来するので、別の名前で clone している
場合は `docker network ls` で実際の名前を調べて読み替えてください。

### LAN のスマホから見えない

- `--host 0.0.0.0` を付け忘れていないか
- 調べた IP アドレスが合っているか（有線と Wi-Fi で別のアドレスを
  持っていることがあります）
- ファイアウォールでブロックされていないか

の順に確認してください。

### `--reload` を付けたまま「本番相当」にしてしまう

打ち間違えて `--reload` 付きで起動していると、ファイルを保存するたびに
再起動が走ります。起動直後の出力に `Will watch for changes` という行が
あれば `--reload` 付きです。本番相当の起動は
`uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` だけです。

## 18.10 やってみよう

解答例は折りたたんであるので、まず自分で考えてから見比べてください。

### 問1 本番相当の起動で `LOG_LEVEL` を渡してみる

18.4 の形で `LOG_LEVEL=WARNING` を渡して本番相当に起動し、第17章で
見えていた `INFO todo-app - ...` のリクエストログがどうなるか観察して
ください。観察したら元に戻します。

??? example "解答例"

    `mytodo/` の中で実行します。`.env` は使わず、環境変数を直接渡します。

    ```bash
    LOG_LEVEL=WARNING \
      uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
    ```

    別のターミナルで `curl http://127.0.0.1:8000/api/todos` を実行すると、
    uvicorn 自身のアクセスログ
    （`INFO:     127.0.0.1:... - "GET /api/todos HTTP/1.1" 200 OK`）は
    出ますが、`INFO todo-app - GET /api/todos -> 200` の行は
    **出ません**。`basicConfig(level=...)` の最低レベルが `WARNING` に
    上がり、INFO のログが捨てられたためです。

    本番では、普段は `INFO` で運用し、調査が必要なときだけ `DEBUG` に
    下げる、といった切り替えを**環境変数の付け替えだけ**でできることが
    わかります。確認したら `Ctrl+C` で止めてください。

### 問2 わざと間違った環境変数で起動して 500 を観察する

存在しないポートを `DB_PORT` に指定して本番相当に起動し、
`/api/todos` がどう応答するか、uvicorn 側のログに何が残るかを
確認してください。第17章のフォールバックハンドラが本番でどう
効くかを確かめる練習です。

??? example "解答例"

    `mytodo/` の中で、DB のポートだけを壊して起動します。

    ```bash
    DB_PORT=55432 \
      uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
    ```

    起動自体は成功します（接続はリクエストのたびに張るためです）。
    別のターミナルで API を叩きます。

    ```bash
    curl -s -w "\nHTTP %{http_code}\n" http://127.0.0.1:8000/api/todos
    ```

    期待される出力:

    ```text
    {"detail":"internal server error"}
    HTTP 500
    ```

    想定外の例外（接続エラー）が、フォールバックハンドラで定型の 500 に
    変換されました。uvicorn 側のターミナルには
    `ERROR todo-app - unhandled error: GET /api/todos` に続いて
    スタックトレース（`psycopg.OperationalError` などの接続エラー）が
    残っています。利用者には定型文だけが返り、原因調査に必要な情報は
    ログに確実に残る、という第17章の方針どおりの動きです。

    本番で 500 に遭遇したら、こうしてログを見て環境変数の誤りに
    気づく、という流れをそのままなぞりました。確認したら `Ctrl+C` で
    止めてください。

## 18.11 最終課題

研修の総仕上げです。ここまで覚えた範囲で、**「自分が欲しい機能」を
1 つだけ追加**してみてください。白紙から考えるのではなく、下の
ステップを 1 つずつこなせば到達できる構成にしてあります。

題材の例（どれか 1 つ、または自分で考えたものを選んでください）:

- ToDo に **メモ（複数行）** を持たせる
- ToDo を **CSV にエクスポート**する画面を付ける
- **完了済みは別タブ** に隠す
- **期限が今日のもの**にバッジを付ける
- **タグ別の件数**をフッタに表示

### ステップ1: 設計メモを書く

テキストファイルに、次の 3 点を 3 行ずつ書き出します。

- テーブル変更は要るか（要るなら、どのテーブルに何の列を足すか）
- API はどうなるか（メソッドとパス、リクエストとレスポンスの形）
- 画面はどう見えるか（どこに何が出るか）

??? tip "ヒント"

    第8章（要件・画面・API の設計）と第9章（テーブル設計）のドキュメントを
    見返すのが近道です。研修本編でやったのと同じ順番で考えればOKです。
    例: 「メモを持たせる」なら、`todos` テーブルに `memo TEXT` 列を足す、
    API は `POST /api/todos` と `PATCH /api/todos/{id}` が `memo` を
    受け取るようにする、画面は詳細欄に表示する、となります。

### ステップ2: マイグレーションを追加する

テーブル変更が要る場合は、`migrations/00X_xxx.sql` を追加して
適用します。要らない機能（CSV エクスポートなど）ならこのステップは
飛ばします。

??? tip "ヒント"

    `init-db` はファイル名の stem（拡張子を除いた部分）をバージョンとして
    記録し、適用済みのものは `skip` します。新しいファイルは
    `003_xxx.sql` のように連番にしてください。何度も試したいときは
    `reset-db` してから `init-db` で初期状態に戻せます。

    ```bash
    uv run python -m app.cli reset-db
    uv run python -m app.cli init-db
    ```

### ステップ3: リポジトリに SQL を追加し、テストを書く

`repositories.py` に SQL を 1 本ずつ追加します。テストも一緒に書きます。

??? tip "ヒント"

    第11章（書き込み）と第12章（テスト）の形そのままです。
    **テストを先に書いて**から実装すると、SQL のミスにすぐ気づけます。
    SQL は必ずプレースホルダ（`%s`）経由にしてください（第6章）。

### ステップ4: API を更新し、テストを書く

スキーマ（`schemas.py`）を更新し、ルーターに足します。httpx の
テストも書きます。

??? tip "ヒント"

    第13章（起動と DI）と第14章（CRUD）の形そのままです。
    バリデーションは Pydantic の型で表現するのが先です。業務ルールに
    近い判定（たとえばメモの上限文字数）は、第17章で扱った
    `services.py` に置いてルーターから呼ぶ形にすると、HTTP と
    分離できてテストしやすくなります。

### ステップ5: 画面を更新する

テンプレートと CSS を更新します。htmx の部分更新が要るなら
フォローも入れます。

??? tip "ヒント"

    第15章（Jinja2）と第16章（htmx）の形そのままです。ユーザー入力を
    出す場所では `| safe` を使わないこと（第17章のセキュリティの
    確認項目）。ブラウザと curl の両方で観察するのは第16章でやった
    とおりです。

### ステップ6: 本番相当の起動で通し確認する

完成したら、**本番相当の起動**で一通り動かして締めます。

```bash
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

完了の条件:

- [ ] 新機能が本番相当の起動（`--reload` なし）で動く
- [ ] 追加・完了切替・削除・フィルタ・検索の既存機能が壊れていない
- [ ] `uv run pytest -v` がぜんぶ緑
- [ ] uvicorn 側のログに、新機能へのリクエストが
      `INFO todo-app - ...` で記録される

??? tip "ヒント"

    手順は 18.3 のままです。うまく動かないときは 18.9 の
    つまずきポイントを確認してください。余裕があれば、18.6 の手順で
    Docker イメージにまとめてコンテナでも動かしてみましょう。

「**薄く 1 周**」すれば、研修で扱った内容のほとんどを使うはずです。
余裕があれば、**コミットを機能ごとに分けて、PR の説明文を書く**
ところまでやると、そのまま実務の流れになります。

## まとめ

- **デプロイ**は、アプリを本番環境に置いて動かすこと。公開先は
  PaaS / VPS / コンテナ基盤の順に自由度が上がるが、自分で面倒を見る
  範囲も増える
- 起動コマンドは**開発用と本番用で別物**。開発用は
  `uv run uvicorn app.main:app --reload --env-file .env`、本番用は
  `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000`。
  `--reload` は開発専用の仕組みなので本番では外す
- 本番の設定は `.env` ファイルではなく、**環境変数を環境側の仕組みで
  渡す**。コードは一行も変えない
- 第17章のログと例外ハンドラは、本番での 500 調査でそのまま活きる
- **Dockerfile** でアプリをコンテナイメージにまとめると、ベース
  イメージと `uv.lock` で環境を固定でき、再現性の問題を消せる。
  `.env` はイメージに含めず、起動時に `-e` で渡す
- インターネットに出すなら、HTTPS・DB の分離・バックアップ・環境変数の
  差し替えが最低限

研修おつかれさまでした。ここまでで触れた主なテーマを並べると:

- Python の型ヒント・dataclass・with・モジュール、pytest の基本
- PostgreSQL の DDL / DML / JOIN / 集約 / トランザクション
- psycopg v3 の接続、プレースホルダ、トランザクション、プール
- 設計（要件・画面・API・テーブル・マイグレーション）と
  Repository パターン
- FastAPI と依存性注入、Pydantic でのバリデーション
- Jinja2 + htmx の軽量 UI
- 設定・ログ・例外ハンドリング・セキュリティ、そしてこの章のデプロイ

ほとんどが「実務でも同じ顔ぶれで出てくる」道具です。あとは作るものが
変わるだけです。さらに先に進むなら、認証と認可、Alembic による
マイグレーション管理、GitHub Actions での CI、構造化ログや Sentry での
観測、大量データでの `EXPLAIN ANALYZE` などが定番のお題です。

困ったら [付録A SQLチートシート](appendix-sql.md) と
[付録B 用語集](appendix-glossary.md) を覗いてください。
